How Muse powers it

Muse is the layer between the posts and the person.

On one side: informal Group posts with no fields at all. On the other: a person with a need, written in one sentence. Neither side is structured. Muse translates both into the same schema, and only then can they be compared.

Seven jobs Muse does in Nest

01

Classify every post

Into 10 categories, from housing listing and lease takeover to roommate request, furniture, and events, so each post is routed to the right extractor.

02

Extract housing

19 typed fields through structured outputs against a strict JSON schema: rent, rent basis, city, neighborhood, coordinates, dates, type, amenities.

03

Look at the photos

Two-pass and multimodal. Text first at minimal reasoning effort; images only when fields are missing. The second pass fills gaps and never overrides text.

04

Build roommate profiles

A second-stage extraction on roommate posts: cleanliness, sleep, smoking, pets, social style as fixed enums, each backed by a verbatim quote checked against the post.

05

Understand the request

One sentence becomes a 13-field search goal: intent, city, neighborhoods, ISO dates, budget, basis, home type, preferences.

06

Resolve places

The prompt carries a live catalog of cities and neighborhoods from our database, so "SLU" and "downtown" resolve to areas that have listings.

07

Ask when it matters

If the city, dates, or budget are missing, Muse returns one short follow-up question. Otherwise it stays out of the way.

Guardrails

Never guess

Null over invention, schema validation before every write, duplicate detection across groups, retries with backoff, a mock adapter fallback, and the key kept server-side.

How we built it

Five features, built in parallel, joined by one pipeline.

We built Nest for people our age with little money, little time, and even less attention. Each of us owned one feature on its own branch, and every feature reads from or writes to the same ingestion pipeline.

  1. 01

    Mock Facebook and the data layer

    An Expo and React Native Facebook shell backed by Supabase Postgres: groups, members, posts, images, and comments, with a seed script that fills them with realistic, messy posts. Nest reads only groups the user belongs to. No scraping.

  2. 02

    Muse service and ingestion

    One AI service interface with two adapters, Muse and a mock. Each post is analyzed once and tracked, so reruns cost nothing. Ingestion is triggered three ways: a realtime database subscription on new posts, a five-minute timer as a safety net, and a bounded freshness check before each search. Output is validated, then checked for duplicates by key and by text similarity.

  3. 03

    Housing search and map

    A TypeScript API interprets the sentence with Muse, then a rule-based matcher scores budget, dates, area, and furnishing. The matcher is one module shared by server and app, covered by unit tests built from real failed searches. Homes that cover only part of a stay are shown and labelled as partial. The map is drawn from raw tiles with pan and pinch-zoom, so it runs in Expo Go and on web with no native SDK.

  4. 04

    Roommate matching

    A background worker turns roommate posts into profiles, single-flight so runs never overlap, and each post is judged once. Compatibility is computed in code as matched, conflict, or unknown per criterion, with budgets within 15% counted as workable. Results are ranked by conflicts, not by an opaque score, and shown as a swipe deck.

  5. 05

    Community

    Event and activity posts are parsed by a deterministic adapter, filtered to the user's city and stay dates, de-duplicated across groups, and ranked by neighborhood and interests. We chose plain parsing here: the format was regular enough that a model would add latency without adding accuracy.

Where AI helped most

Executing a plan we had already made

  • Scaffolding screens, schemas, and the ingestion and matching code from a written brief shared by every teammate and every coding agent.
  • Writing tests, then turning each real failure into a new test.
  • Debugging with evidence: we log every query and what Muse understood, so an agent could replay a failed search against the live server and find the cause.
Where it fell short, and what we changed

Guessing, latency, and rigid logic

  • Muse guessed a home type and invented a "downtown" neighborhood, returning zero results. We moved to fixed enums and validate neighborhoods against the database.
  • Muse-written roommate explanations added about 8 seconds per search. We moved explanations into code and made the model optional.
  • AI-written matching was all-or-nothing. We rewrote it around what a person would actually pay, and cut interactive retries from six to two.

Use the model to understand. Use code to decide.
